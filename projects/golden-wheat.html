Overview

A client engagement to replace spreadsheet-and-paper reporting in a single-site flour mill with a governed, auditable information system. This page is a sanitized public summary of the architecture approach. It contains no client data, figures or commercial details.

Problem

Production data lives in fixed Excel templates and scanned paper reports spread across departments. Without a central store, the company cannot trace a raw-material lot through production to the finished product and customer, reconcile inventory against production, or link periodic quality samples to the lots they describe.

Architecture

Source files never write directly to the database. Each upload is checked for duplicates by file hash, loaded into staging, validated, shown to the user as a preview, and only then confirmed into a single atomic write. Reporting reads from read-only views, so dashboards cannot alter operational data.

Key design decisions

DECISION01

Append-only stock ledger

Inventory is a ledger of transactions that is never edited in place. Corrections are new adjustment transactions, which keeps history reconcilable and auditable.

DECISION02

Many-to-many lot traceability

Raw-material lots and finished-product lots are linked through explicit relations, because blending means one lot can feed many outputs and the reverse.

DECISION03

Modular monolith, single database

One Django application and one PostgreSQL database give transactional consistency and simple operations. Kafka, microservices and a separate data warehouse are not justified at this data volume and team scale.

DECISION04

Data-driven configuration and access control

Master data, templates and mappings are configuration, not code. Role-based access control with an audit log restricts sensitive data to authorized roles.
